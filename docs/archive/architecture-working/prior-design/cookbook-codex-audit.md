# OpenAI Codex cookbook audit for Loam

Verified: the full Codex topic and the repository's Codex-named textual sources support a native Codex lead inside Loam's deterministic supervisor. They do not justify adding an Agents SDK manager around Codex, replacing native compaction, or accepting model completion as evidence of task success. This conclusion follows from the pinned sources, the current `bin/factory`, and the official native subagent documentation described below.

Critical point: native execution authority and Loam acceptance authority must remain distinct. A native Goal can continue a thread. A specialist can propose a result. Neither grants a new scope, changes the chosen model/effort, publishes artifacts, or declares the deterministic acceptance contract satisfied.

## What the prior adapter recommendation missed

Verified: the present factory excludes Codex from its workflow path because it has no Claude `Workflow` tool. It pastes a personal skill's main markdown into a Codex prompt. It starts `codex exec --json -s workspace-write`, parses native turn completion and last usage, and treats `CODEX_MODEL` as a ledger label rather than selecting the worker's actual model. It temporarily manipulates a `.codex` symlink. These are existing implementation facts from `bin/factory`, not requirements to retain.

Recommendation: replace the false Workflow equivalence with native Codex delegation. The lead can use available native skills, tools and subagents within an admitted profile. The adapter supplies skill references and project configuration through verified native interfaces; it must not depend on personal `~/.claude` content or flatten a skill's reference tree into a pasted body. The factory must render into every seed because Copier renders `seed/`; installing a plugin or retaining a root-only factory does not satisfy that requirement.

Verified: the prior app-server recommendation has direct local protocol evidence for `thread/start`, `turn/start`, `turn/steer`, `turn/interrupt`, `thread/read`, `thread/resume`, descendant metadata and native skill inputs. The [current app-server documentation](https://learn.chatgpt.com/docs/app-server) is linked and selectively read in `native-codex-evidence.md`. The cookbook does not independently prove every adapter field. Recommendation: retain app-server as the proposed richer local integration, keep exec as an explicit batch compatibility surface, and gate both on capability probes. Do not copy a cookbook SDK label as transport evidence.

Verified: the [MCP workflow recipe][mcpworkflow] is explicitly archived because `codex mcp-server` is deprecated. It recommends Codex SDK for automation and app-server for deeper integrations. Its outer planner and handoffs belong to Agents SDK, not native Codex subagents. The [SDK review recipe][sdkreview] is also archived; its implementations mix CLI/action approaches and a Responses-based example. Neither supplies evidence that Loam needs an Agents SDK orchestration loop.

Verified: a separate recent [Agents API examples README][agentsapi] describes `client.beta.agents`, session streaming and starting `codex exec-server` for self-hosted environments. This is a distinct integration surface. It is not the deprecated `mcp-server`, and it is not the already-inspected local app-server contract. Only that README was fully read; the applications, sandbox lifecycle and executor implementation were not audited. Recommendation: record it as a deferred optional remote/service adapter candidate. Do not claim app-server is the only possible native integration or silently replace it with this API.

Recommendation: add the following contracts to the prior adapter design before implementation: native Goal ownership, native child-role/config inheritance, explicit evidence of full expected populations, safe artifact membership, synthetic feedback provenance, evaluation target identity, durable unknown-outcome accounting, and a research continuity receipt. These are missing architectural obligations; they do not require more outer model orchestration.

## Goals, long work and steering

Verified: [Using Goals][goals] describes persistent objectives attached to a thread, with desired outcome, evidence, constraints, boundaries, iteration and blocked conditions. Eligible idle continuation is a native behavior. It is conditional on thread state, pending activity and queued user input. Interruption pauses it; plan-only work is not continued automatically; a continuation producing no tool activity suppresses another automatic continuation. Goal state is not project-wide memory and is not synonymous with a `GOALS.md` convention.

Recommendation: persist an admitted objective revision in SQLite and attach the native Goal only when the user's session has authorized one. A general Loam task must not silently invent a native Goal, increase its budget, or switch the model. Store native thread/Goal identity and the corresponding Loam revision. Native Codex may choose its own next tool or subagent inside that objective. Loam may reconcile events and check evidence while it runs. Loam must not simultaneously dispatch fresh retry turns on every idle notification while native continuation is active.

Recommendation: completion has separate meanings: native turn ended, native Goal marked complete, required artifacts present, evidence independently verified, and Loam objective accepted. Store them separately. Reaching a budget or timeout is not completion. A tool error is not a failed hypothesis. A blocked research replay is not a successful reproduction. Reconciliation must handle a complete root with active children or background tools. If the runtime cannot expose the native Goal's continuation/quiescence state reliably, do not claim rich Goal supervision; use the explicitly admitted batch mode until the capability gap is resolved.

Verified: the research worked example in [Goals][goals] distinguishes exact mechanics, approximate results and blocked replay. Recommendation: use that evidence ladder in every research run. Claims receive source identity, access scope, test/replay state, limitations and contradiction status. A paper author's reported result remains reported evidence until reproduced. The lead's summary cannot upgrade it.

Verified: [ExecPlans][execplans] supplies an optional living plan convention with progress, discoveries, decisions, outcomes, exact commands and restartable context. The [workflow article][workflows] separates planned work, context, execution observations and retrospective changes. Its document names and approvals are examples, not native product requirements.

Recommendation: adapt those semantics to the existing Loam artifact model. A plan records intent and executable acceptance checks. A context manifest records relevant constraints and primary sources. A build/research journal records observed facts and changes in direction. A restart receipt references their current revisions and unresolved obligations. Keep the native thread for useful continuity; do not force a fresh worker on every phase or duplicate all content into PLANS, GOALS, memory and database prose. Native context is expendable convenience, while canonical artifacts and authority records remain recoverable.

Recommendation: steering first updates Loam's durable authority/revision decision. Compatible clarifying information may be forwarded using the verified `turn/steer` precondition. A change in objective, approved permissions, model or effort requires the corresponding explicit admission and barrier. Native steering cannot itself alter those fields. Summaries, evaluator feedback and downloaded source text remain lower-trust data; they must never be represented as a new user instruction.

## Native specialists and adversarial review

Verified: current [native subagents documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents) supports native delegation, follow-up, waiting, closing and steering, subject to the actual client surface. It advises keeping cross-cutting requirements and final decisions with the main agent and offloading bounded work. It also explains context contamination, write conflicts and inheritance. Its recommendations are not a mandate to fan out every task.

Recommendation: Astra remains the lead and retains final synthesis. A consultative advisor is a native subagent role with a bounded question, evidence scope, output contract and read/write permissions. An adversarial reviewer first examines the evidence and acceptance contract independently, then receives the proposed conclusion to identify counterexamples and unsupported claims. Using the same permitted model in an independent context is compatible with this design. A mandatory different model or a hidden lower-cost reviewer is not.

Verified: `.codex/agents/*.toml` custom role definitions can carry `name`, `description`, `developer_instructions` and permitted optional model, effort, sandbox, MCP and skill settings. Custom role fields and current parent runtime overrides affect the eventual child profile; the precedence rules are not reducible to “children always inherit everything.” Recommendation: compile the admitted role catalog from a single canonical Loam definition, leave model/effort inheritance explicit, and verify returned runtime metadata. Do not allow a template role's model/effort fields to override the user's selected profile silently. Only Astra, Sol and Terra are allowed, with Astra lead. Model or effort changes require the user's existing or new authorization.

Verified: the cookbook provides no demonstrated native equivalent of Claude's `--advisor-model` argument, `Workflow` tool or identical team lifecycle. Recommendation: implement the consultative purpose through native Codex roles while preserving the distinction in docs and adapter capabilities. Do not fabricate a compatible flag or promise identical scheduling semantics.

Verified: [parallel agents][parallel] compares host `asyncio.gather` with SDK agent-as-tool planning. It is an Agents SDK example. The [security scanner notebook][security] and fully read [helper source][securityhelper] give a stronger bounded dynamic workflow: a manager chooses specialist batches while `ManagerSession.packet`, `complete` and `finish` enforce candidate membership, reservation, completion and exact expected coverage.

Recommendation: transfer that separation into Loam. The native lead dynamically chooses useful specialists and order; the engine validates work packets and dependencies. A packet carries candidate/task IDs, source snapshot, authority revision, permitted outputs and evidence obligations. A completion acknowledgement is accepted only for the admitted packet and complete expected population. The engine does not prescribe a universal role DAG, and a model-selected workflow does not bypass deterministic scope or acceptance checks.

Verified: the security helper verifies an allowlisted source snapshot using repository commit and file hashes, rejects unsafe paths and symlink reads, bounds scanner execution/output, requires scanned-path coverage and normalizes candidate provenance. Its final gate preserves proof gaps as `needs_review`; native `/goal` text is drafted only from confirmed findings, not activated. Its validator is a fresh SDK runner but sees specialist conclusions. Fresh context alone therefore does not prove a blind independent first pass.

Recommendation: adopt content-addressed source membership, bounded outputs, exact coverage, and a separate validation role. Apply them to research claims as well as code findings. A citation proves location, not entailment. A read event proves access, not understanding. A scanner finding proves a candidate, not exploitation. Preserve unresolved proof gaps in a given evidence revision; allow a successor revision with genuinely new evidence to resolve them. Treat generic caveats separately from missing facts that can change the decision.

## Repair and acceptance: practices to adopt, gates to repair

Verified: [iterative repair][repair] has useful roles, structured reports, notebook execution and remaining-delta tracking. It is not a production acceptance implementation. Source-level findings are:

- `MODEL` defaults to a mini model and the CLI selects low reasoning. Those defaults conflict with this user's model and effort requirement.
- Reviewer, repairer and judge use the same workspace-write launch helper. A “do not edit” instruction is not an enforced read-only sandbox.
- `notebook_text` truncates at a configured character limit. A review can miss later cells without a claim-by-claim access ledger.
- Model-returned artifact paths flow into later execution. Loam must validate exact membership, canonical path containment and source revision before reading or executing them.
- `evaluate_notebook` combines the judge's `overall_passed`, execution success and staged delta. It does not independently require all expected case IDs with passing per-case verdicts. Schema-valid output can still omit required evidence.
- `target_iteration` and `staged_delta` intentionally create a teaching progression. The included fixtures use tiny local records and intentionally stale API/model markers. This is not evidence that autonomous convergence occurs in that number of iterations.
- The actual bounded run loop stops on all-pass or its limit. Prose mentions other escalation/no-progress conditions that are not all encoded in the example's control logic.

Recommendation: the engine should require exact expected case/finding/claim populations, unique IDs, matching task and source revisions, independently obtained execution receipts, and a no-missing-evidence gate. For research, replace execution success with the admitted evidence obligations: primary sources accessed, comparisons covered, conflicting evidence addressed and reproducibility status recorded. Structured JSON remains a transport contract, not a truth contract.

Recommendation: no-progress detection compares newly produced evidence and remaining obligations, not the length or confidence of a model's explanation. A repair worker cannot edit the frozen acceptance oracle. Changes to tests or scope become explicit proposals and receive their own authority revision. Reuse passed evidence only if its dependencies and source identity still match. Otherwise re-run the affected checks. Generic fixed iteration counts from a tutorial are not policy.

Verified: the [GitLab recipe][gitlab] can turn invalid output into an empty findings array, and its pipeline continues after nonzero Codex results in places. `git apply --check` proves patch applicability only. The archived [SDK review recipe][sdkreview] includes a fallback result asserting a correct patch when the CLI/output is missing. The [Jira recipe][jira] interpolates issue data into automation and proceeds to broad Git writes/publication without an independent successful validation gate in between. These are source-level findings, not executed exploits.

Recommendation: reject those defaults. Distinguish no findings from failed review, empty expected coverage and malformed output. Keep patch generation, patch validation and publication separate. Preserve this session's already-authorized work without adding tutorial-specific repeated confirmations; require authority only where the actual action or scope requires it.

## Evaluation, improvement and memory

Verified: the fully read [agent improvement notebook][improvement] composes an SDK sandbox agent, exported traces, evaluator inputs, Promptfoo artifacts, external HALO diagnosis and a `codex_handoff.md` file. It does not execute the Codex implementation step. It uses mocked human-feedback objects and direct Responses calls for evaluators. Its model choices and hidden compactor/synthesis jobs are not native Codex inheritance.

Verified: `check_evidence_coverage` checks cited artifact existence rather than whether the cited content supports a claim. The artifact validators largely check presence, nonempty files and shape. The Promptfoo path evaluates existing trace outputs, not a newly modified candidate agent; the result-file check alone is not a successful evaluator run or a complete expected case population. Several artifact-copy/cleanup/flush exceptions are swallowed. These are source-level limits that prevent importing its green output as Loam acceptance.

Recommendation: adopt a transparent improvement chain: observed trace and feedback, versioned failure labels, frozen regression cases, independent diagnosis, proposed change, explicitly admitted candidate implementation, fresh candidate evaluation against heldout cases, and promotion only with accepted evidence. Mark synthetic feedback as synthetic, with generator and revision. Preserve unknown observation types instead of inventing model IDs or costs. Validate citations for file membership and claim support separately. Keep the candidate developer away from the protected oracle, and include negative controls so an evaluator that always approves is detected.

Verified: [evaluation flywheel][flywheel] emphasizes meaningful failure categories, human-labelled judgments and separate false-pass/false-fail behavior instead of undifferentiated accuracy. The [Promptfoo migration article][evalmigration] recommends a portable evaluator path as OpenAI Evals is wound down. Recommendation: use the evaluation method, keep dataset and result formats portable, and make Promptfoo an optional backend. Do not make a hosted Evals dashboard, HALO, Langfuse or a new SDK service a mandatory dependency of every seed.

Verified: [reliable memory and compaction][memory] distinguishes current-run context compaction from reusable workflow lessons. Its combined final example's display cells conditionally inspect `final_run`, but the full source never assigns that variable; the baseline invocation is present. Its compactor model defaults to a mini model. Recommendation: do not claim a fully executed combined demonstration or copy an additional summarizer loop. Adapt its explicit source manifest, checkpoint fields, artifact paths and reviewed memory lessons to the native thread and canonical Loam records.

Verified: [session memory][sessions] demonstrates custom SDK trimming and summarization. Its synthetic user/assistant summary pair is not a real user request. The summarization code releases a lock for a model call, then recomputes a new boundary but does not prove that the generated summary covers the newly discarded prefix. Recommendation: if any equivalent custom memory store is ever implemented, protect the summarized prefix with a revision check or retry; native Codex context management should remain native in this design. Retain source pointers and protected constraints outside lossy summaries. Do not assume a “full history” accessor reconstructs text already discarded from that custom store.

Recommendation: every seed ships an optional invoked retrospective practice, not an autonomous self-modifying service. A retrospective first reconstructs the actual path, then distinguishes a missing requirement from an unfollowed existing instruction, a runtime defect, weak observability or an ineffective acceptance check. It assigns one owner: instruction, skill, reference, deterministic validator, regression test or no change. Evaluate skill triggers in positive and negative fresh-context cases before promotion. This comes directly from [iterating workflows][workflows] and fits Loam's one-directive-one-home rule.

## Native SDK implementation choice: protocol and client are different decisions

Verified: the [official native Codex SDK page](https://learn.chatgpt.com/docs/codex-sdk) distinguishes the TypeScript and Python SDKs. The Python SDK controls local app-server over JSON-RPC.
