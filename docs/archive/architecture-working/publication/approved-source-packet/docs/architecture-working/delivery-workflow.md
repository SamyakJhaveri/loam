## Who implements and who reviews

Accepted review rule for building Loam:

| Implementation lead | Required plan reviewer | Required finished-work reviewer |
|---|---|---|
| Codex/Astra | Actual Claude Code Fable 5.1, fresh review context | Actual Claude Code Fable 5.1, fresh review context |
| Claude Code/Fable 5.1 | Actual Codex/Astra, fresh review context | Actual Codex/Astra, fresh review context |

A free-standing native reviewer or a predefined subagent is acceptable if its actual model and independence satisfy that row. A Codex subagent labeled Fable is not Claude review. An advisor that helped produce the solution cannot count as its independent reviewer. Reviewers receive requirements, criteria, relevant source access and the exact plan/diff, not the author's conversation or a prior favorable verdict. Their context and file access exclude author scratch material, persistent provider memory and the ticket's earlier review reports. Required reviewer identity that cannot be established from native evidence leaves that review pending; no self-reported identity substitutes. Plan review and finished-work review are separate observations. Record each author/helper's actual provider/model. Prefer implementation helpers from the lead's provider under the admitted model/effort profile; opposite-provider consultation can remain advisory. If both providers contribute implementation, split that ownership into separate steps or obtain fresh independent reviews from both providers covering the full integrated candidate. No contributor reviews its own work, and no review of one portion substitutes for the required opposite-model coverage of another.

Recommendation: use Codex/Astra for core TypeScript, storage and recovery integration; use Claude/Fable for Claude-native workflow/advisor integration. For other tickets choose the seat with the clearest verified capability and available context. Preserve the user's model/effort choices; do not silently use another model after a limit or unsupported feature. If the required review seat is unavailable, record review pending and do not merge; independent authorized work may continue.

## Repeatable ticket cycle

1. Fetch remote main and use that fetched head as the exact step base. A locally diverged main is reported and preserved, never silently folded into the base or reset. Record the exact base commit. Create the step's fresh branch/worktree from that latest main, not an older stage branch. Preserve the current untracked design records first and make the reviewed plan/reference packet available to workers without copying secrets or using a stale private cache as authority.
2. Write the bounded ticket from the consolidated stage: requirements, source-reading packet, scope/exclusions, expected outputs, implementation owner, opposite-model reviewers, failure cases and checks. Wayfinder may help if available and useful; ordinary ticket authoring is sufficient. A six-stage plan is not six giant commits: split stages into independently reviewable, testable steps.
3. Obtain opposite-model plan review before implementation. Record the digest of the exact ticket plan and its source/criteria packet, criteria revision, reviewer provenance, actual inspected scope and findings. Resolve blocking findings or narrow the plan under user authority. Material plan changes need review of the changed plan; an old receipt does not approve them.
4. Implement using the appropriate native loop. Tests/checks run during development, not only at the end. Helpers receive bounded ownership and handback requirements. Use disjoint scopes or child worktrees based on the recorded step base; they integrate into the owning step, not independently into main. Required missing work remains pending. Do not let helpers reset or discard unrelated changes.
5. Capture an independent opposite-model review of the exact finished candidate and relevant source/test evidence. Repair confirmed issues and revalidate the changed candidate, including a fresh opposite-model review receipt for its changed diff. Unchanged independent evidence can remain linked, but cannot certify unreviewed changes. A lean critic is optional additional scrutiny, never a substitute for this review. Repeated confirmed blockers remain blockers; a repair cap is an incomplete outcome, not a pass.
6. Freeze the final candidate and record required focused checks plus one designated validation-owner `bin/check` run requiring `check: PASSED`. The integration owner may also be the designated validation owner; there is still one named full-check assignment. Bind both code review and checks to that candidate. Where a stage requires both hosts, record both host results against the same candidate with their environment identities; one Mac check does not certify Linux. If main advanced, integrate its current changes into the step, resolve conflicts and refresh review/check evidence for the resulting candidate before merging. An earlier clean test run does not certify a later merge result.
7. Merge the reviewed, verified step into main under the user's requested sequential integration policy and repository protections. Record the frozen candidate tree identity, then check that merged main has that same tree and the required integration/CI result. Squash/rebase may change commit identity; a different resulting tree needs renewed checks/review before progression. Record the merge identity and next-step handoff. Only then create the next dependent step from refreshed main. A failed integration check is repaired or explicitly reconciled before progression.

The user has requested this merge-after-review sequence for implementation steps; retain that standing authority once implementation begins rather than asking for the same routine merge approval repeatedly. Still obey actual repository protection and tool approval requirements. This is not permission to bypass checks, overwrite unrelated work, publish a release, deploy or send unrelated messages. No merge or runtime implementation occurs in this planning step.
