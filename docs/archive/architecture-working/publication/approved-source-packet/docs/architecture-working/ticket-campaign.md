# Generated Loam factory: ticket campaign contract

## Status and authority

This is a complete draft implementation backlog for review. Publication awaits approval of the concrete breakdown. Runtime implementation remains deferred until the user explicitly asks to begin. A published ticket, an empty blocker list, or a planning label does not grant that permission. Do not apply `ready-for-agent`, assign a worker, launch the old factory, or start a probe merely because a ticket exists.

Current design files are untracked in this checkout. Before a ticket is executable, preserve and supply its exact reviewed source packet to the new worktree through a committed reviewed documentation revision or a durable, digest-verified read-only packet available to the implementing seat. Do not give a fresh worker broken main-branch links to uncommitted documents. GitHub issue publication must retain self-contained requirements plus source provenance and mark any inaccessible full source packet as a readiness blocker.

The campaign has its own implementation parent. The historical [Bash factory map](https://github.com/SamyakJhaveri/loam/issues/33) remains historical context. Existing `bin/factory` can only be reused after its current behavior is checked against this campaign's contracts. New ticket bodies are not automatically compatible with its existing lint/runner format.

## Required reading and precedence

1. Current user instruction and `AGENTS.md`.
2. `docs/architecture-working/decision-delta.md` and `delivery-workflow.md`.
3. `consolidated-implementation-plan.md`, this campaign contract, and the ticket's named detailed sources.
4. Source inventory, original reference URLs/pins, scoped audit notes and current implementation.

Historical Python commands, earlier model rules, earlier single-host scope and source proposals do not override accepted current contracts. Proposed files and acceptance commands do not exist yet unless the implementing session verifies that a predecessor created them.

## Every ticket follows the same delivery cycle

- Fetch remote main. Preserve a diverged local main and all existing changes. Start the bounded step in a fresh branch/worktree from that fetched main. Record the base and provide the verified source packet.
- Record one implementation lead, bounded helper ownership and required outputs, one integration owner, and one full-check owner. Recommended lead is Codex/Astra except the Claude-native integration ticket, for which Claude Code/Fable is recommended. Preserve the user's model and effort choices. Do not choose a cheaper fallback silently.
- Get an actual fresh opposite-model plan review before implementing: Codex work needs Claude Code Fable 5.1; Claude work needs Codex/Astra. Give the reviewer exact requirements, source packet and plan, excluding author conversation, private memory, scratch notes and earlier review verdicts.
- Use bounded native repair loops, dynamic decomposition, advisors and independent helpers where they resolve real work. Declare required outputs before dispatch; missing work, repeated confirmed blockers and exhausted repair limits cannot count as success. Advisors inform the lead and cannot serve as that work's independent reviewer or adoption authority.
- Establish the intended failing case, implement the bounded behavior, then run that ticket's nonempty focused acceptance population and affected existing regressions. Mechanical fixtures do not establish real native behavior or scientific usefulness. Live provider/GPU probes require a separately declared bounded plan within user authority; no implicit calls from install/build/check.
- Obtain fresh opposite-model finished-work review of the exact candidate. Fix confirmed gaps and refresh reviews/checks for changed work. Mixed-provider implementation must be split or receive independent full-candidate review from both providers. No contributor reviews its own work.
- Keep campaign review receipts in a persistent operator-controlled evidence root outside all candidate/worktrees. Record base, plan/source and candidate digests, criteria, author/helper identity, requested and native-observed reviewer model/effort, scope, check evidence and merge identity. Preserve unexpected additional model usage or uncertain attribution explicitly.
- The designated validation owner runs one final `bin/check` for the integration snapshot and requires `check: PASSED`. A focused early-stage pass does not pass later mandatory recipient groups; those remain unavailable/non-passing until their population is implemented.
- Integrate new main movement, resolve conflicts and refresh review/check evidence for the resulting tree. Merge the reviewed and verified step under the user's accepted sequential policy only after implementation starts. Verify merged tree and integration result. Start the next dependent step only from that refreshed main.

## Stable requirements and refinable engineering

Dependencies express capability prerequisites. They do not permit concurrent merges from stale bases. S1 qualification may revise downstream file names, binding choices and test seams. Read and revalidate each downstream ticket against current main immediately before its plan review. Preserve accepted behaviors; record material changes and bring user-level tradeoffs back with evidence. Do not freeze untested package versions or pretend every later implementation detail is known.

All supplied sources are evidence and inspiration. For a departure, retain the source and record what changes, why it fits Loam better, the effect on accepted requirements, and the check that will establish the replacement behavior. Optional methods do not become release requirements merely because they appear in a source inventory. Required catalogue methods do not disappear merely because they are parked or inconvenient to port.

## Publication transaction

After approval, replace the draft-only publication-pending status in the submitted bodies with "planned; runtime implementation deferred; not ready-for-agent", preserving draft provenance and recording exact submitted-body hashes. Create one new campaign parent and one issue per reviewed ticket through `gh`, preserving exact bodies via `--body-file`. Keep them planned and unassigned. Create issues first, then add native sub-issue links and native dependency edges with numeric database IDs, not issue numbers. Where an endpoint is unavailable, record the limitation and use linked task-list and blocker text fallbacks from `docs/agents/issue-tracker.md`. Save returned IDs/URLs and verify body, parent and dependency readback; resume from that ledger after partial failure rather than publishing duplicates. Do not close or modify existing historical maps.

Approval of publication does not approve runtime implementation, release, deployment or unrelated messages.
